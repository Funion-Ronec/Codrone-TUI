CODRONE-TUI  v0.2.0
===================
Two terminal flight consoles, one shared code base:

    python edu_tui.py           CoDrone EDU        real drone over the USB controller   (cyan/amber theme)
    python sim_tui.py           CoDrone Simulator  the Unity simulator on this PC       (violet/green theme)
    python Codrone-TUI.py       asks which one   (or: Codrone-TUI.py edu|sim ...)

Run them with the project's venv:   .venv\Scripts\python.exe edu_tui.py --demo
Use Windows Terminal (or any terminal with Unicode + truecolor); the graphs are braille characters.

Options (both):   --demo        mock drone, nothing flies. Try everything safely.
                  --connect     pair immediately
                  --port X      EDU: COM port (default: auto-detect)   Sim: host:port (default 127.0.0.1:5000)
                  --theme X     btop, catppuccin-mocha, tokyo-night, gruvbox, nord, textual-light ...
                  --field PATH  field layout file (default field.toml)
                  --no-log      do not write typed commands to logs/ (see `log` below)
Simulator only:   --no-verify   do not probe the simulator on connect

The two TUIs deliberately look different so a real drone is never mistaken for the simulator.


LAYOUT  (rovr-style bordered panels, btop-style graphs)
------
  status bar   link, battery, flight state, job count, match clock + score, mode, uptime
  1 Console    log + command prompt          2 Sidebar   click / enter to run common commands
  3 Telemetry  battery meter, braille graphs (front range, height, speed), attitude, position, sensors
  4 Processes  running / queued / finished commands
  5 Map        top-down field, drone, trail   (+x forward = right, +y left = up)
  6 Score      Solo Autonomous scorecard + 180 s clock     7 Metadata   backend, firmware, session stats
  8 Pilot      keystroke HUD for PILOT mode: lit keys, stick bars, speed, tricks, bound commands
  The layout adapts to the terminal size (auto). `p` cycles presets: auto, full, flight, pilot, mission, minimal, focus.

KEYS
----
  NORMAL mode keys act; INSERT mode (cursor in the prompt) types a command; AUTO means a mission is flying.
  ctrl+x   EMERGENCY STOP - works everywhere, even while typing.
           EDU: motors cut (the drone drops).  Simulator: sends `land` (the sim has no motor cut).
  ctrl+l   urgent land: drops everything queued, then lands
  esc      (NORMAL) soft stop: cancel queued / automatic moves, hover      (in the prompt: leave it)
  i  :  /  start typing        tab or ->  accept suggestion       up/down  history
  1-8      show/hide panel     p  layout preset      t  cycle theme     ?  help     q  land + quit
  ctrl+p   command palette (every shell command, fuzzy searchable)
  f        PILOT mode (below)


PILOT MODE  (fly with the keyboard)
----------
  `f` (or the `pilot` command) enters it and shows panel 8; `esc` or `f` leaves it and the drone hovers.
  Default keys:
    hold W A S D   forward / left / back / right        hold J / L   turn left / right
    hold Q / E     down / up                            I / K        speed + / -  (5 levels: 15-80% stick)
    T  take off    G  land now (`land -e`)              1 2 3 4      flip front / back / left / right (EDU)
    F1-F4  shape square / circle / spiral / triangle (EDU)   F5 / F6  mission run hover_test / takeoff_land
  Keys that are not pilot keys keep working (`:` or `/` opens the prompt, `?` help, `p` layout).
  ctrl+x / ctrl+l always win.

  Let go of every key and the drone hovers. The sticks only fly while the drone is linked, flying and
  nothing else is queued: a takeoff, flip or mission pauses them (HUD shows BUSY).
  On Windows the TUI reads the real key-down state, so holding feels like a game, but only while its
  window is in front (HUD shows NO FOCUS otherwise). Elsewhere it guesses from key repeats: a tap moves
  for about half a second. On the real EDU the first `f` of a session asks you to confirm.

  Rebinding (saved to pilot_keys.toml, loaded on start):
    pilot keys                       list every binding
    pilot bind forward up            bind an action to a key   (-f takes the key from whatever had it)
    pilot bind forward               ... or press the key you want next (esc cancels)
    pilot run f7 mission run phase1  bind a key to any command  (quote it if it has flags: "land -e")
    pilot unbind f1                  free a key          pilot reset    back to the defaults
    pilot speed 3                    set the speed level
  Actions: forward back left right turn_left turn_right up down speed_up speed_down takeoff land
           flip_front flip_back flip_left flip_right toggle.   esc, ctrl+x, ctrl+l can't be rebound.


COMMANDS  (type `help`, or `help <command>`)
--------
  link      pair [port]    disconnect    ports    status    info
  flight    takeoff    land [-e]    stop    estop    hover [s]
            forward|backward|left|right|up|down <cm> [speed]    (aliases f b l r u d)
            go <dir> <cm>    turn [left|right] <deg>    tl/tr [deg]    stick <roll> <pitch> <yaw> <thr> <s>
            wait <s>   flip [front|back|left|right]  (EDU, battery >= 50%)   shape square|triangle|circle|spiral|sway (EDU)
  gadgets   led <r> <g> <b> | off     beep [hz] [ms]
  simulator grab   release   teleport <x> <y> <z>   resetpos
  general   help  clear  echo  cat <file>  history  log [on|off]  source <script.txt>  exit [-f]
  ui        theme [name]   layout [name]   toggle <panel>
  autonomous  see below

Commands queue and run in order on a flight thread, so the UI never freezes. Exceptions:
  `land -e`, `stop`, `estop` jump the queue.  A plain `land` waits its turn (so a typed sequence still flies in order).
`source file.txt` runs one command per line (# comments allowed). `exit` lands first if flying (`exit -f` quits at once).
Every command you type is logged to logs/codrone-command-log-<time>.txt (one file per session, created on the
first command). To turn that off: start with --no-log, or put `commands = false` under [log] in config.toml,
or type `log off` (`log on` turns it back on, plain `log` shows which it is). With logging off no file is created.
The ADC attempt history (logs/adc_attempts.json) is separate and not affected.
Compared with the old draft: `echo` no longer runs your text through a shell, `pair <port>` no longer also prints
"Invalid Argument", `exit` really lands the drone (the old check compared a method to True), and `direct`/`flip`
placeholders are replaced by `go`/`stick` and a real `flip`.


AUTONOMOUS  (Aerial Drone Competition 2026-27, "Mission 2027: Fast Track", Game Manual v1.1)
----------
Rules implemented (manual section 4, Solo Autonomous Flight): 180 s, up to 3 attempts, drone runs on pre-programmed code,
resets allowed with the clock still running, tasks in any order, up to their maximum count:

    take off 5 x1 | red arch 5 x2 | blue arch 5 x2 | green keyhole 10 x2 | yellow keyhole 20 x2 | large cube 25 x2
    mini keyholes #1 #2 #3: 15 x2 each | spiral bonus 10 x2 | tunnel 15 x2 | landing once: pad 5 / any cube 10 / bullseye 15
    theoretical maximum = 290

Spiral bonus (4.2.2): crediting mini_3 awards it automatically only if the last three credited tasks were mini_1, mini_2,
mini_3 in that order. Any other credited task in between breaks it. `undo` removes a bonus together with its trigger.

Workflow:
    preflight                     checklist from the manual (battery, state, eye protection, flight zone, observer ...)
    preflight confirm all         tick the human items once they are really done
    mission list                  routines + predicted points            mission dry <name>   predict score/time, no drone
    mission run <name>            practice run (does not use an attempt)
    mission run <name> -m         timed MATCH attempt: clock starts, routine credits go on the match scorecard
    match start | reset | finish [pad|cube|bullseye|none] | abort | status | new | piloting <score>
    credit <task>...  undo  landing <pad|cube|bullseye|none>  score      judge / correct the card by hand
    mission stop (or esc)         stop at the next step              match reset   count a drone reset (clock keeps going)

  * Routine credits are what the routine CLAIMS. Nothing can see a gate, so a person must `undo` anything the drone missed.
  * The clock expiring aborts the routine and lands the drone (flying on after zero is a foul in the manual).
  * Routines refuse to start unless the drone is on the ground (they assume the programming mat at the origin, facing +x).
  * Attempts, best score and skills total (best autonomous + best piloting) persist in logs/adc_attempts.json.
  * On a REAL EDU every `mission run` asks for confirmation and shows the checklist first (`-y` skips the dialog;
    failed automatic checks, e.g. low battery, refuse the run either way).
  * The `min_battery` pre-flight threshold (default 40%) is a team setting, NOT an RECF number.

Built-in routines: hover_test, takeoff_land, phase1 (red arch > green keyhole > cube), spiral (mini 1>2>3),
phase3 (blue arch > yellow keyhole > tunnel), full_run (laps while time remains, then bullseye).

Your own routines: drop a .py file in routines/ (see routines/example_square_gate.py):

    from codrone_tui.adc.routine import routine

    @routine("my run", "what it does")
    def my_run(ctx):
        ctx.takeoff()
        ctx.through("red_arch")        # lines up, flies through, claims the points
        ctx.forward(80); ctx.turn(90)  # plain moves (cm / degrees, + = clockwise)
        ctx.land_on("pad")

  ctx also has: goto(x, y[, z]), up/down/left/right/backward, hover, wait, credit(key), time_left(), log().
  Every ctx call checks for a stop request first, so esc / ctrl+l can interrupt between steps.
  Files in routines/ are executed (it is your code); a broken file shows up as "<name> (load error)" instead of crashing.

!! FIELD CALIBRATION - READ THIS BEFORE FLYING A REAL MISSION !!
  field.toml holds the element positions the routines fly to (cm from the centre of the green first foot of the
  programming mat, where the drone starts; +x forward up the long leg, +y left, +z up; `heading` = direction of travel
  through the element; the tunnel has `vertical = true`: it is flown DOWN through, from its top opening, manual fig 3.1.5).
  Where the numbers come from (adc-manual-v1.1.pdf, the copy in this folder):
    * SIZES  - manual section 1.5.2 (arch opening 60"x63", keyhole 24" inner, large cube 17"x17"x20", pad 30" with a 10"
               bullseye, tunnel 23.5"x19", mat 96"x42")                                      -> official (approximate)
    * LAYOUT - Figure 3.2.2: an L. Two mats end to end up the long leg (red arch over the start of the pad, then green
               keyhole, then large cube); the field turns RIGHT, and the blue arch, yellow keyhole and tunnel follow
               along the short leg, with the mini-keyhole tower at the corner.
    * x / y  - read off that figure with a ruler grid (about +-10 cm)                        -> ESTIMATES
    * z      - heights of the stands are not in the manual                                   -> GUESSES
  The official "Game Element Assembly and Field Setup" document (real measurements) returned HTTP 403 when fetched, and
  the manual allows +-3 in of variation between fields (7.3.2). So: measure YOUR field, edit field.toml, set
  `calibrated = true`, then `mission reload`. Until then the UI shows "placeholder field" on the map and in every dry run.
  Routines navigate by dead reckoning (the commanded moves), not by sensing the gates. A keyhole's clear opening is only
  24" (61 cm), so a drift of a few tens of cm decides whether a gate scores: expect to tune moves on the real field.
  After takeoff the routines take the real hover height from the downward range sensor (EDU and simulator).

Source for the rules: adc-manual-v1.1.pdf in this folder = https://games.recf.org/adc/1.1  (Game Manual v1.1, Sept 29 2026).
The manual's own revision history says a v1.2 MAY follow on Nov 10 2026 and a MAJOR v2.0 on Dec 22 2026 "that may include
changes to gameplay": the scoring table and field above are a snapshot. Rules get updated and the RECF Q&A overrides the
manual - re-check before a competition, and update codrone_tui/adc/rules.py if the points change.


SIMULATOR NOTES
---------------
  * The vendor library cannot tell whether the simulator is running (UDP). `pair` therefore probes a range query and says
    clearly if nothing answers (--no-verify skips the probe). Its socket has no timeout, so we set one (1 s).
  * No battery / attitude / position read-back exists: position on the map is dead-reckoned and marked "est.".
  * Moves return before the simulator finishes them, so the TUI sleeps an ESTIMATED time per move (config: sim.cm_per_s,
    default 80). Tune it if a routine's timing looks off. Climbing is a timed throttle burst (sim.vertical_cm_per_s).
  * There is no motor cut: estop = `land`.

EDU NOTES
---------
  * The vendor library calls exit() when the controller cannot be opened and reports success even when the drone is off;
    both are handled (clear error messages; the drone's state is checked after pairing).
  * Importing codrone_edu replaces asyncio.sleep with a browser-only version that crashes the UI; we undo that on import.
    The import itself takes ~1.7 s (numpy, Pillow), so it runs in the background while the UI comes up.
  * Serial writes are locked so telemetry polling and flight commands never interleave.
  * `flip` is refused below 50% battery (the library silently ignores it; we tell you).


CONFIG  (optional config.toml next to the scripts; every key has a default)
------
    [ui]   theme = "btop"   layout = "auto"   poll_hz = 5.0
    [edu]  port = "COM5"    min_battery = 40
    [sim]  cm_per_s = 80.0  vertical_cm_per_s = 60.0  verify = true
    [pilot] speed = 2   rate_hz = 20.0   hold = "auto"   ("repeat" = always guess from key repeats)
    [log]  commands = true                               (false = no command log file)

KNOWN LIMITS
------------
  * Written and tested without a CoDrone EDU or the Unity simulator at hand: the EDU and Simulator backends are tested
    against faithful fakes (see tests/test_real_backends.py). First flight on real hardware: use --demo to learn the keys,
    then `mission run hover_test`, over a clear floor, with eye protection.
  * Gate crossings are claimed by routines, never detected.
  * Several details of vendor-library behaviour (units, flight-state names, what `pair` does on failure) come from reading
    its source code, not from flying it. If something reads wrong on real hardware, tell me and it is a one-line fix.
